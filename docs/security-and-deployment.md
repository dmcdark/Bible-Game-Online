# 游戏安全说明

本文件只记录已实现的安全防护、仍存在的风险和可选改进。
以下改进表中的编号固定，后续新增项目从末尾追加，方便按编号讨论实施顺序；编号不代表优先级。

## 已实现的安全防护

- **防止网页脚本注入**：昵称、排行榜等动态文本转义；动态颜色仅接受六位十六进制色值。
- **浏览器安全策略**：增加 CSP、禁止嵌入和 MIME 嗅探等响应头，并移除两款游戏的 HTML 内联事件；样式暂时仍允许内联写法。
- **缩小公开文件范围**：只开放必要前端资源，服务端代码、环境文件、依赖清单和持久数据不作为静态文件公开。
- **校验输入**：限制昵称、字段类型、整数范围、API JSON 和 Socket.IO 消息大小；异常输入返回错误。
- **限制资源滥用**：最多 100 个房间、每间 8 人、200 个 Engine.IO 连接，每个识别来源最多 40 个已建立游戏连接；限制连接、建房、入房、消息和成绩提交频率。
- **清理占用状态**：房间 30 分钟没有有效进度或存在满 6 小时后关闭；限流记录设置容量上限并清理过期项。
- **验证联机权限**：检查房间成员、房主、当前行动者、随机回合编号和阶段，拒绝越权、旧回合及重复操作。
- **服务端判定联机结果**：服务端生成随机结果并计算位置、信心值等状态，不接受浏览器覆盖玩家状态、终点标记、题库长度、昵称或颜色。
- **保护排行榜写入**：数据单独保存、串行写入、临时文件原子替换；保存失败不发布内存成绩，无法解析的数据不被悄悄覆盖。
- **检查访问来源**：生产环境必须设置 PUBLIC_ORIGIN；Origin 检查只限制浏览器来源，不作为玩家身份认证。
- **保守处理代理头**：默认不信任 X-Forwarded-For；游戏 Nginx 模板覆写来源头，并设置站点请求和连接限制。
- **降低容器权限和资源占用**：非 root、只读程序目录、移除 capabilities、禁止提权，限制 CPU、内存、进程和日志大小；应用端口仅映射到本机回环地址。
- **降低构建依赖风险**：按锁文件安装，不执行依赖安装脚本；第三方 Action 固定提交 SHA，发布前检查依赖高危和严重漏洞。

## 仍存在的安全边界

- 单人成绩仍由浏览器上报，范围检查和限流无法证明成绩真实，不适合可信竞赛或奖品结算。
- 前端题库和公开源码中可查询答案，服务端判题不能阻止查答案。
- 四位房间号不是私密凭据；目前没有登录、私密邀请或稳定玩家身份认证。
- 非浏览器程序可以省略或伪造 Origin，CORS 和来源白名单不能阻止所有外部程序访问。
- 客户端对局日志只限制长度、数量并以纯文本显示，内容不保证真实，不作为服务端判定依据。
- 代理可能隐藏玩家真实 IP，使多名玩家共享来源限额；不能靠直接信任所有转发头解决。
- Docker 共享宿主机内核，独立网络不等于禁止出站访问；当前没有完整限制容器访问宿主机、内网和云元数据。
- 房间和限流状态仅在单进程内存中；重启会重置限流计数，当前保护不能跨多个实例统一生效。
- 自动检查不能证明不存在漏洞；规则和接口检查不能代替浏览器安全验证、受控滥用测试或渗透测试。

## 可继续优化的安全项目（尚未实现）

| 编号 | 安全项目 | 成本较低的做法 | 限制与取舍 |
| --- | --- | --- | --- |
| 1 | 限制容器出站访问 | 确认必要连接后，针对游戏容器网络限制宿主机、内网和云元数据访问 | 需先核对实际路由和 Docker 防火墙，不能套用全局清空或阻断规则；仍共享宿主机内核 |
| 2 | 防止猜房间号加入 | 保留四位编号，增加可选的随机邀请凭据和入房失败限流 | 私密房间需要凭据，必须在服务端验证；只隐藏房间号无效 |
| 3 | 减少单人成绩伪造 | 先在榜单标明“浏览器上报成绩” | 标注成本低但不防作弊；可信成绩需要服务器维护并判定单人对局 |
| 4 | 减少提前获取答案 | 联机只下发当前题目，答案保留在服务端，结算后揭示 | 公开仓库里的相同题库仍可查询；离线模式不能真正保密，前后端需同步调整 |
| 5 | 增加身份和访问控制 | 私密房间先采用第 2 项邀请凭据，需要稳定身份或权限时再加入登录 | 公开匿名游戏不必为了 CORS 增加账号；登录不能单独阻止刷请求，需设计凭据保护和失效机制 |
| 6 | 防止伪造重要对局日志 | 服务端根据已接受动作生成重要日志 | 当前纯文本处理已降低脚本注入风险，此项主要保证记录可信度 |
| 7 | 准确识别来源并限流 | 核对实际代理链，只信任明确的代理来源及由其覆写的 IP 头 | 前级已丢失真实 IP 时，信任网桥也无法恢复；不能直接信任任意 X-Forwarded-For |
| 8 | 扩大安全验证范围 | 补充恶意昵称、越权、重放、异常输入和共享来源限额的受控验证 | 自动检查不等于安全保证，滥用和负载验证应在隔离测试环境进行 |

表中各项只是方案，不代表已修改代码或服务器。断线重连、对局保存和多实例扩容属于功能或可用性改进，不列入本安全实施清单；如果以后实现，还需单独设计座位恢复和跨实例权限校验。

## 方案、优缺点与待讨论事项

本节供原作者评估是否需要实施，不作为本次已完成的功能。编号与上表一致，实施范围和顺序待讨论确定。

### 1. 限制容器出站访问

**方案**：先确认游戏运行时需要哪些外部连接，再按游戏容器网络限制主动访问互联网、宿主机、内网和云元数据。保留反向代理到游戏的访问及正常响应。宿主机拉取镜像与游戏运行时的出站权限分开处理。

**优点**：即使应用被利用，也能减少扫描内网、访问云凭据接口或向外传输数据的机会；通常不增加玩家操作。

**缺点**：需要按实际网络和 Docker 防火墙后端配置，同时考虑宿主机流量、转发流量及 IPv6。错误规则可能导致游戏无法访问；以后新增邮件、第三方登录或在线资源，需要重新放行。仍不能消除共享内核的风险。

**待讨论**：是否提供可选的部署加固说明，由部署者按环境应用，而不在项目中自动修改全局防火墙。

### 2. 防止猜房间号加入

**方案**：保留四位房间号，建房时可选公开或私密。私密房间使用服务端生成的长随机邀请凭据，服务端验证后才允许加入；凭据随房间关闭失效，错误尝试另行限流。

**优点**：降低陌生人猜中编号进入房间的机会；公开房间可以保留现有加入流程；邀请链接方便分享。

**缺点**：私密房间多一个分享或输入步骤；邀请被转发后，接收者仍可能加入。凭据需要避免出现在普通日志和容易泄露的 URL 参数中，并设计失效机制。

**待讨论**：是否保持公开房间为默认选项；采用邀请链接、单独邀请码，还是两者都支持。

### 3. 减少单人成绩伪造

**方案**：低成本做法是标明“浏览器上报成绩”，作为娱乐榜单。若需要更可信的成绩，可保留原单人玩法，另加联网计分模式，由服务器维护对局、生成随机结果并计算成绩，可信榜只接收该模式结果。

**优点**：标注方案改动小，保留现有体验；服务端计分方案能够阻止直接提交任意分数，并区分本地成绩与服务器验证的成绩。

**缺点**：标注不能防作弊。服务端计分需要更多状态管理和资源，网络断开可能中断计分，需要设计恢复方式；仍不能阻止查答案、脚本操作或代答。

**待讨论**：排行榜定位是轻量娱乐分享，还是需要投入成本做服务器验证；两类成绩是否分榜展示。

### 4. 减少提前获取答案

**方案**：联机只发送当前题目和选项，服务器保留正确答案并判题，答题后再揭示；同时调整静态文件开放范围，避免直接下载完整答案。

**优点**：减少从当前页面数据中直接读取答案的机会，为服务端判题划清数据范围。

**缺点**：需要同步修改前端题目读取和显示逻辑。同一题库若仍用于离线玩法，答案可能从离线资源获取；公开仓库和历史版本中的题库已经可以复制，移除网页中的答案不能让公开内容重新保密。

**待讨论**：是否接受这项有限收益；是否需要区分联机与离线题库，而不是追求无法保证的答案保密。

### 5. 增加身份和访问控制

**方案**：先与第 2 项合并，用邀请凭据控制私密房间访问。只有需要固定成员、管理员、账号封禁或跨设备身份时，再考虑第三方登录和会话管理。

**优点**：邀请凭据不要求所有玩家注册；账号系统则能为成员身份和权限管理提供依据，减少仅凭昵称识别玩家的混淆。

**缺点**：邀请凭据不证明真实身份；账号系统增加登录流程、外部服务依赖、隐私处理和会话维护。登录本身也不能阻止刷请求、多个账号或凭据分享。

**待讨论**：是否只需要“允许进入这个房间”，还是需要“识别同一个账号”。不为解决 CORS 而单独引入账号系统。

### 6. 防止伪造重要对局日志

**方案**：由服务器根据已接受的动作生成掷骰、答题、位置、信心变化和回合结束等重要日志，客户端只负责展示。优先替换现有对局显示日志，不默认增加长期审计数据存储。

**优点**：日志与服务端实际结果保持一致，减少客户端编造记录的机会；改动相对集中，正常玩家无需额外操作。

**缺点**：需要迁移相关文本生成逻辑，修改玩法时同步维护日志；如以后长期保存审计日志，还会增加磁盘占用、轮转和隐私处理需求。不得记录邀请或会话秘密。

**待讨论**：哪些日志必须由服务端生成；是否只在对局中展示，暂不新增长期保存功能。

### 7. 准确识别来源并限流

**方案**：先核对实际代理链。真实 IP 能被安全传递时，只信任明确的代理来源，并由代理覆写转发头；若来源已经丢失，则保留站点总量、连接、房间和会话限流，不强行声称能够恢复真实 IP。

**优点**：减少正常玩家共享来源配额的误伤；分层限制可以降低单一 IP 判断不准确带来的影响。

**缺点**：配置依赖具体代理环境，信任范围过大会让伪造 IP 绕过限流。家庭、学校和公司网络仍可能共享 IP；会话限流也可能被反复重连绕过，不能替代站点总量保护。为保留 IP 改变入口结构还会增加部署复杂度。

**待讨论**：是否先保持保守默认值，提供明确的代理配置说明；共享来源情况下，如何根据实测人数调整配额。

### 8. 扩大安全验证范围

**方案**：优先增加针对已知风险的小型自动测试，再做双设备人工验证。覆盖恶意昵称、房外操作、非当前玩家、旧回合、重复消息、伪造状态、异常数据、共享来源限额，以及未来私密邀请的验证和失效。滥用与负载测试在隔离环境进行。

**优点**：安全规则更容易复现和检查，上游更新时可以较早发现回归；测试也能明确哪些操作应该被拒绝。

**缺点**：测试需要随功能维护，会增加 Actions 时间和用量；自动测试无法覆盖所有浏览器和部署环境，也不能证明不存在未知漏洞。负载测试可能耗尽测试环境资源。

**待讨论**：先约定少量必须通过的安全用例，再按真实需求扩展，不默认在生产服务上压测。

### 建议的讨论顺序

- 优先考虑 **6、8**：先提高日志可信度并覆盖关键安全规则，避免引入账号或改变加入流程。
- **2、5 合并评估**：按私密房间需求决定是否实施，避免重复建设身份控制。
- **1 先核对环境再实施**：属于部署层防护，适合提供可选指导，不自动修改部署者的全局网络配置。
- **7 保守调整**：先确认来源信息能否保留，再决定代理信任与配额。
- **3 按榜单定位决定，4 可后置**：防作弊成本较高，且都不能保证杜绝作弊。

## 安全验证范围

- 动态昵称包含尖括号和引号时，等待室、提示、玩家列表及排行榜仍按文字显示。
- 私有文件返回 404，页面和 Socket.IO 脚本包含预期的安全响应头。
- 房外、非当前玩家、错误阶段、旧回合及重复请求不能改变游戏结果；伪造玩家状态被忽略。
- 错误类型、超大消息、非法 JSON、跨来源请求和突发请求被拒绝，服务不因这些输入退出。
- 排行榜并发提交和写入失败不会发布未保存成绩；数据目录不会被当作静态目录公开。
- 验证容器非 root、只读目录、端口回环绑定及资源限制实际生效。
- 依赖公告检查通过不代表基础镜像、所有系统包或未知漏洞已被完整扫描。

已配置的自动检查和实际完成情况以对应 GitHub Actions 运行日志为准，未完成的人工安全验证不能因构建成功而省略。

## 后续修改的安全要求

- 上游修改玩法时，同步核对服务端规则，避免前后端不一致导致绕过判定。
- 不能为了排查连接问题直接关闭输入校验、回合校验或全局信任代理头。
- 不把 .env、私钥、凭据、排行榜数据和敏感日志提交到 Git。
- 定期审查依赖与基础镜像安全更新；需要独立内核隔离时使用单独 VM/VPS，不能把 Docker 视为绝对隔离。
